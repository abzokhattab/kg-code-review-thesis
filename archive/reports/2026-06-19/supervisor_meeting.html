1What I actually built

A tool that reviews a code change four different ways, then a panel of AI judges scores all four to see which way produces the best review.

When a developer proposes a code change (a "pull request" / PR), an AI can read it and write review comments. But the raw change only shows what lines changed. It doesn't show the things an experienced reviewer checks by clicking around the project:

  • Which other parts of the code call this function (so a change here might break them)
  • Which test files cover this code (so you know what to re-run)
  • What depends on it elsewhere in the project

My system feeds the AI that surrounding context automatically. We compare four "modes":

ModeWhat the AI is givenThink of it as...
BaselineJust the code change + its descriptionA reviewer who only sees the diff
KG (knowledge graph)+ a map of callers, tests, dependenciesA reviewer who knows how the code connects
RAG (retrieval)+ similar code snippets from elsewhereA reviewer who's seen similar code before
Hybrid+ both of the aboveA reviewer with both kinds of context

2How the experiment works (the flow)

Same pull request goes through all four modes, then every review is scored the same way. Nothing is hand-picked — it's an automated pipeline.

Why 3 judges instead of 1? So no single AI's bias decides the outcome. We take the majority vote of the three. We also checked that the judges agree with each other — they do (see "κ" in the glossary). This is the AI-research equivalent of having three reviewers instead of trusting one.

What each review is scored on

A 25-point checklist built from published code-review research (Bacchelli & Bird, Google's review practices, ISO software-quality standards). Each item is a yes/no question like "Does the review name the specific test files to update?" or "Does it warn about breaking changes to dependent code?"

Of those 25, 9 are "structural" questions — the ones that need exactly the knowledge our context provides. Those 9 are the fair test of whether KG helps.

3Reading the numbers (plain English)

Four symbols show up in the results. Here's what each one means, in everyday terms.

Mean / average score (e.g. 4.97 out of 9)
Just the average number of checklist items a review got right. Higher = better review.
Δ (delta) (e.g. +0.60)
How much better a mode scored than the baseline. "+0.60" means it got, on average, 0.60 more checklist points than the diff-only baseline. A plus sign is good.
p-value (e.g. p = 0.007)
The chance the improvement is just random luck. Smaller is better. Below 0.05 is the scientific bar for "this is real, not a fluke." p = 0.007 means about a 0.7% chance it's luck — very convincing.
d_z (effect size) (e.g. +0.47)
How big the improvement is in practice. Rule of thumb: 0.2 = small, 0.5 = medium, 0.8 = large. So +0.47 is a solid medium-sized effect.
κ (kappa) (e.g. 0.59–0.72)
How much the 3 judges agree with each other. 0.6–0.8 is called "substantial agreement." Ours sits right in that band — the judges are consistent, so the scores are trustworthy.

5Who wins when (the key nuance)

KG and RAG don't compete — they're good at different things. This is the most important finding to land with your supervisor.

KG wins
on STRUCTURAL questions
"Does it mention the specific callers / tests / dependents?" KG carries those exact facts, so it scores best here. p = 0.007.
RAG wins
on GENERAL coverage
"Is the overall review thorough?" RAG pulls in similar code, helping broad commentary. It wins the full 25-point total. p = 0.007.
Hybrid (both together) wins on both. Combining the two improves the structural questions and the general total. So the honest story isn't "one method beats the other" — it's "each method helps the thing it's designed for, and combining them helps everything." That complementary result is more credible than claiming one approach dominates.

7Questions your supervisor might ask (with answers)

"Why only 40 PRs?"
Each PR is reviewed 4 ways and scored by 3 judges on 25 items — that's 12,000 scored cells. We chose 40 with pre-set selection rules across 5 languages for diversity. The effect holds across that diversity; a bigger sample is future work.
"Why trust AI judges instead of humans?"
The 3 judges agree substantially (κ = 0.59–0.72), and the human study is being run precisely to confirm they match human preference.
"Doesn't 'GraphRAG' hype say knowledge graphs beat everything?"
Our honest finding is complementarity, not dominance: KG wins structural criteria, RAG wins general coverage, hybrid wins both. That's a more defensible claim.
"Is the improvement actually meaningful or just statistically significant?"
Both. The effect size (d_z ≈ 0.47–0.58) is a genuine medium-sized effect, not a tiny technically-significant blip.
