Knowledge Graph–Driven Context Retrieval for LLM-Based PR Review

A systematic comparison of Knowledge Graph vs. RAG vs. Hybrid context strategies for improving the quality of AI-generated code review comments

Author: Abdelrahman Khattab Supervisor: Prof. Dr. Holger Giese Advisor: Dr. Christian Adriano Institution: Hasso Plattner Institute, University of Potsdam Date: January 2026
Executive Summary

This proof-of-concept demonstrates that augmenting LLM prompts with structural repository context significantly improves the quality of generated PR review comments. Using a Knowledge Graph to provide information about tests, dependencies, and code relationships enables the LLM to generate more specific, actionable, and technically accurate feedback.

Part 1

The Review Gap

AI code generation tools (GitHub Copilot, ChatGPT) have dramatically accelerated how fast developers write code. But code review hasn't kept pace—creating a dangerous bottleneck.

📊 The Review Gap Problem
10x
Code Generation Speed
(with AI assistants)
≫
1x
Review Capacity
(still human-limited)

Result: PRs queue up waiting for review. Quality suffers. Bugs slip through.

Why Existing AI Review Tools Fall Short

🔍
Limited Context
Most AI review tools only see the code diff. They can't access the broader codebase—so they don't know what tests exist, what files depend on the changes, or how the code fits architecturally.
📝
Generic Feedback
Without codebase context, LLMs produce vague advice like "consider adding tests" instead of "extend UserServiceTest.java to cover this new validation logic."
⚠️
Missed Integration Risks
LLMs can't warn about breaking changes if they don't know which files import the modified code. They miss architectural concerns without seeing the dependency graph.
💡 Our Hypothesis

If we enrich the LLM's input with structural codebase knowledge—information about tests, dependencies, and related files extracted from a Knowledge Graph—it can generate more specific, actionable, and accurate code review feedback.

Part 2

Research Questions

This proof of concept investigates two key questions:

🔬 RQ1: Does KG Context Improve Review Quality?

When we provide the LLM with information about tests, dependencies, and related files, does it generate more useful, specific, and actionable review feedback?

Finding: Yes, +68% improvement over baseline
🎯 RQ2: Which Criteria Benefit Most?

Which aspects of code review quality are most improved by KG context? We evaluate against 25 criteria, 9 of which specifically require codebase knowledge.

Finding: Breaking change warnings (+40%), Test mentions (+20%)
Part 3

How It Works: The Pipeline

We process each Pull Request through a 4-stage pipeline that builds context and generates evidence-anchored review notes.

1
Extract PR Data
Get the code diff, changed files list, and PR metadata from GitHub
2
Build KG Context
Find related tests, dependent files, and code relationships using static analysis
3
Generate Review
LLM (GPT-4o) generates structured review using diff + KG context
4
Evaluate Quality
LLM judge scores against 25 criteria from literature-based checklist [1-4]
Part 4

Four Generation Modes Compared

We systematically compare four approaches to understand what type of context helps most. Each mode adds a different type of information to the LLM's input.

🎯 What Each Mode Sees
Input Type Baseline RAG KG Hybrid
Code Diff ✓ ✓ ✓ ✓
PR Metadata (title, body) ✓ ✓ ✓ ✓
Similar Code Chunks (semantic) ✗ ✓ ✗ ✓
Nearest Test Files (structural) ✗ ✗ ✓ ✓
Dependent Files (structural) ✗ ✗ ✓ ✓
Import/Call Relationships (structural) ✗ ✗ ✓ ✓
1. Baseline
Diff Only
The LLM sees only the code changes. No codebase context at all. This is what most current AI code review tools do.
ANALOGY

Like reviewing a book edit without having read the book. You can check grammar, but can't verify if the edit fits the story.

Limitation: Can only comment on what's visible in the diff
2. RAG
Semantic Context
Uses vector embeddings to find code chunks semantically similar to the changed code. Good for finding patterns and related implementations.
ANALOGY

Like having a search engine that finds "code that looks similar." Useful for consistency, but doesn't know relationships.

Limitation: Doesn't know which files are tests or dependencies
3. Knowledge Graph
Structural Context
Extracts explicit relationships from the codebase: which files are tests, which files import the changed code, architectural dependencies.
ANALOGY

Like having a map of the codebase. You know exactly which tests cover this code and what will break if you change it.

Strength: Can name specific test files and warn about dependent code
4. Hybrid
Full Context
Combines KG + RAG. Gets both structural relationships (tests, deps) AND semantically similar code. The most comprehensive context.
ANALOGY

Like having both the map AND a search engine. You know the structure and can find related patterns.

Best of both: Structural accuracy + semantic coverage
📝 Same PR, Four Different Reviews

PR #14778 (Apache Kafka): Adds remote.fetch.max.timeout.ms configuration parameter.
Here's exactly what each mode says about test coverage:

1. Baseline (Diff Only) 48%

What it says:

"Insufficient test coverage for the new feature... Enhance test coverage in DelayedRemoteFetchTest.scala to include edge cases."

❌ Problem: Generic. Guessed the test file name from the changed file name. Doesn't actually know if this test file exists.
2. RAG (Semantic Context) ~45%

What it says:

"Similar timeout configurations in the codebase use validation. Consider following the pattern in FetcherConfig.java... Add tests similar to existing config tests."

⚠️ Partial: Found similar patterns semantically, but doesn't know the actual test file structure or dependencies.
3. Knowledge Graph (Structural) 40%

What it says:

"Add unit tests in DelayedRemoteFetchTest.scala [exists in KG] to cover scenarios with different timeout values. Also update RemoteLogManagerConfigTest.java [exists in KG] for config validation."

✓ Specific: Names actual test files from the KG. Knows they exist and can be extended.
4. Hybrid (KG + RAG) 52% ⭐

What it says:

"Enhance DelayedRemoteFetchTest.scala with test cases for the new timeout. Based on similar configs, add validation in RemoteLogManagerConfig.java. Note: KafkaApis.scala imports this module—verify integration."

🏆 Best: Combines specific file names (KG) with pattern insights (RAG) + warns about dependencies.
🔑 The Key Difference

Without KG Context

"Add tests for this feature"

→ Developer must search for relevant test files

With KG Context

"Extend DelayedRemoteFetchTest.scala line 45"

→ Developer knows exactly where to add tests

Part 7

Evaluation: Literature-Based 25-Criterion Rubric

Reviews are scored using an LLM-as-judge protocol (GPT-4o-mini) against a 25-item checklist synthesized from foundational code review research. The criteria cover what makes code reviews useful according to empirical studies at Microsoft [3], Google [2], and academic research [1,4].

Methodology: LLM-as-Judge Evaluation

Following Zheng et al.'s LLM-as-judge framework, we use GPT-4o-mini to systematically evaluate each generated review against our 25 criteria. This approach is more reliable than simple text similarity metrics (like BLEU or SBERT), which Hong et al. showed can be misleading for code review evaluation.

Why These Criteria? Research Foundation

Our 25 criteria operationalize findings from empirical research on what makes code reviews effective:

Bacchelli & Bird (ICSE 2013) [1]

"Developers expect reviews to find defects, improve quality, share knowledge"
→ Our F1-F4 (Functionality) + M1-M3 (Maintainability)

"Google reviews focus on readability, correctness, maintainability"
→ Our C1-C6 (Code Quality) + R1-R5 (Robustness)

Part 9

Ablation Study: Which Context Features Matter? (RQ2.1)

To understand which parts of the KG context contribute most to review quality, we systematically removed features and measured the impact.

🔬 Experiment: Remove Tests vs Remove Dependencies

We systematically removed KG features and measured the impact on review quality scores.

Configuration Avg Score vs Full KG Impact
Full KG (all features) 20.8% — Baseline
KG − Dependencies (no importers/callers) 16.0% −23% Critical
KG − Tests (no test coverage) 17.3% −17% High impact
KG Minimal (files only) 12.5% −40% Severe
📊 Ablation Findings

Dependencies Are Critical (−23%)

Removing dependency information causes the largest quality drop. The LLM loses ability to warn about breaking changes and integration risks.

Tests Are Valuable (−17%)

Test coverage info enables specific recommendations about which tests to run and what edge cases need coverage.

Full KG Is Best

Combining all features (tests + deps) yields highest quality. Minimal KG (−40%) shows structural context is essential.

⚠️ Ablation Limitations
  • Small sample (3 PRs) — results are indicative, not conclusive
  • Single run per configuration — no variance measured
  • LLM-based evaluation may have noise
  • Full thesis will include more systematic ablations
Part 10

Limitations & Threats to Validity

🔴 External Validity

  • 10 PRs from 7 repositories
  • Results are comparative case studies, not broad generalization
  • All PRs are from large, well-maintained OSS projects

🟡 Construct Validity

  • LLM-as-judge evaluation may have systematic biases
  • 25 criteria rubric adapted from established code review literature [1-4]
  • No human spot-check validation in PoC (planned for thesis)

🟣 Implementation Gaps

  • RAG mode: Partial implementation, retrieval failures on 2 PRs
  • Function-level calls: Using file-level imports instead of AST-based call graphs

🔵 Model Sensitivity

  • Single run per PR (no variance reporting)
  • GPT-4o for generation, GPT-4o-mini for evaluation
  • Temperature = 0.3 for generation
📝 Notes on Results

Why are absolute scores low (12-24%)?

The 25-criterion rubric is intentionally strict—many criteria (e.g., "reference specific test files by name") require information that may not always be relevant or available. Even expert human reviewers wouldn't satisfy all 25 criteria on every PR. The key insight is the relative improvement (+68-97%), not the absolute score.

Why does KG beat Hybrid in PR2?

In 2 of 10 PRs, KG outperforms Hybrid. This suggests that in some cases, RAG retrieves irrelevant or noisy context that dilutes the quality of KG's structural signals. Future work will investigate when to prefer KG-only vs. Hybrid based on PR characteristics.

Why is PR4 missing?

PR4 from Mariotto's dataset was excluded due to repository access issues during the PoC phase. The full thesis will include additional PRs to compensate.

Part 11

Conclusions

✅ RQ1.1 Answered

Yes, context augmentation improves review quality. KG mode shows +68% improvement over baseline. Hybrid achieves +97%. 8 out of 10 PRs benefit from structural context.

✅ RQ1.2 Answered

Hybrid (KG+RAG) performs best overall, winning 7/10 PRs. KG-only wins 2/10. RAG-only not fully evaluated due to implementation issues. Combining structural + semantic context yields most comprehensive reviews.

📊 RQ2.1 Preliminary

Dependencies are the most critical KG feature. Ablation shows removing deps hurts quality by −23%, followed by tests (−17%). Minimal KG (files only) causes severe degradation (−40%). Full thesis will expand ablation scope.

🔑 Key Insight

KG enables specific, actionable feedback (naming actual test files, warning about dependent code) vs. generic baseline advice. This specificity is the primary driver of quality improvement.

⚠️ Important Finding (RQ1)

Without evaluation criteria that properly address software artefacts (tests, dependencies, integration points), the LLM cannot demonstrate benefit from richer context. Generic criteria fail to capture KG-specific improvements. This motivates refining KG-relevant criteria into sub-categories.
